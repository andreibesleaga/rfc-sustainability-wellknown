                The 'sustainability-data' Well-Known URI
               draft-besleaga-sustainability-wellknown-09

Abstract

   This document defines the "sustainability-data" well-known URI, at
   which a web origin publishes a JSON document declaring the energy
   consumption, carbon footprint, and related environmental and
   sustainability metrics of a target: the organization behind the
   origin, the origin itself, a part of it, a service, a device, or a
   product, for different reporting periods.  The declaration links to a
   methodology and may carry a signature, name the declarations of
   upstream providers, and link to third-party attestations.  The
   metrics are self-asserted claims of the publisher.  This document
   registers the well-known URI and the media type application/
   sustainability-data+json.

1.  Introduction

   Organizations increasingly publish energy and carbon figures:
   corporate greenhouse-gas accounting [GHG-PROTOCOL] defines the
   quantities, reporting regimes such as [EU-CSRD] require them, and the
   IAB workshop report [RFC9547] records the need for such data about
   Internet systems and the gaps in it.  What is missing is a fixed
   place and form in which the figures an organization already produces,
   usually for a reporting year or a month, can be found and read by
   software that knows nothing but the organization's web origin.

   This document defines both.  The place is a well-known URI [RFC8615].
   The form is one small JSON document, the _declaration_, which a
   publisher can write by hand from its report and serve as a static
   file.  Its mandatory target member names what it is about: an
   organization, an origin, or a narrower target such as a path, a
   service, or a tenant of a provider (Section 1.1).  A publisher that
   keeps monthly or per-service figures can publish several objects in
   one array, and can answer queries for a range of periods or for one
   target.  A publisher that does neither serves one file and ignores
   the query.  A small conformant declaration carries the seven
   mandatory members and at least one metric or evidence link; this one
   also classifies its target and states its unit:

   {
     "updated": "2026-03-01T12:00:00Z",
     "capabilities": "basic",
     "provider": "Example Corp (sustain@example.com)",
     "measurement-method": "cloud-billing",
     "methodology-uri": "/sustainability/methodology",
     "period": { "start": "2025-01-01", "end": "2025-12-31" },
     "target": "Example Corp",
     "target-type": "organization",
     "carbon-footprint": 4140,
     "carbon-unit": "kgCO2e"
   }

   How figures are measured, and whether any figure is true, are outside
   the scope of this document.  A consumer retrieves the declaration
   (Section 2), reads it (Section 3), takes every value as a claim of
   the publisher of the origin that served it, verifies a signed member
   when it chooses to, and follows the evidence links when it needs them
   (Section 5).

1.1.  Terminology

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
   "OPTIONAL" in this document are to be interpreted as described in BCP
   14 [RFC2119] [RFC8174] when, and only when, they appear in all
   capitals, as shown here.

   *  *Origin*: the scheme, host, and port triple of an HTTP URI
      ([RFC9110], Section 4.3.1; the web origin of [RFC6454]).

   *  *Publisher*: the party operating an origin and publishing a
      declaration from it.

   *  *Consumer*: any client that retrieves a declaration.

   *  *Declaration*: a JSON document as Section 3 defines it: one
      declaration object or an array of them.  An origin's declaration
      is served at its well-known URI; an upstream entry may name one
      served elsewhere (Section 3.5).

   *  *Declaration object*: a JSON object carrying the members of
      Section 3.2 and Section 3.3, about one target for one period.

   *  *Target*: what a declaration object is about, named by its target
      member: an organization, an origin, a path of an origin, a
      service, a product, a device, a tenant, or a data source.

   *  *Server*: the origin server for the well-known URI ([RFC9110],
      Section 3.6), or an intermediary answering on the publisher's
      behalf ([RFC9110], Section 3.7); whichever server answers, the
      declaration is the claim of the origin's publisher (Section 5.1).

2.  The Well-Known URI

2.1.  Location and Transport

   The declaration is published at the path /.well-known/sustainability-
   data on the origin, with the media type application/sustainability-
   data+json; this document registers both (Section 8).  A declaration
   MUST be published and retrieved over HTTPS.  A consumer MAY also
   process a 200 OK response whose Content-Type is application/json as a
   declaration; a response carrying any other media type is not a
   declaration.  Access control, caching, and every other aspect of the
   HTTP exchange are as [RFC9110] and [RFC9111] define them and are the
   publisher's to configure.

2.2.  Query Parameters

   A server MAY support the query parameters target, start, end, and
   granularity, carried in the query component of the URI ([RFC3986],
   Section 3.4) in the usual name=value form.  A server that does not
   support a parameter ignores it and answers the rest of the request; a
   static file therefore satisfies every request.  The start, end, and
   granularity parameters are defined by the following ABNF [RFC5234],
   using the case-sensitive string notation of [RFC7405] and the full-
   date rule of [RFC3339], Section 5.6:

   start       = %s"start=" full-date
   end         = %s"end=" full-date
   granularity = %s"granularity=" granularity-value
   granularity-value = %s"yearly" / %s"monthly" / %s"daily"
   full-date   = <full-date, see [RFC3339], Section 5.6>

   The value of the target parameter is a target member value
   (Section 3.2); a path prefix begins with "/".

   A server that supports these parameters selects, from the declaration
   objects it holds, those that satisfy every parameter it honors, and
   returns them as a JSON array in ascending order of period.start.  An
   object satisfies start and end when its period has at least one day
   in common with the range they bound, both bounds included; an absent
   bound is unbounded.  It satisfies the target parameter when its
   target member equals the parameter's value, compared as Section 3.2
   says.  It satisfies granularity when its period is a whole calendar
   year, month, or day respectively.  A server returns what it holds, as
   it holds it, and computes no aggregate.  When nothing is selected,
   the response is an empty array.

   Because a server may ignore any parameter, a consumer MUST compare
   the period and target of every object it receives with what it
   requested, and MUST NOT record a response as covering a period or a
   target it does not name.

2.3.  Partial Answers

   A publisher declares the target it can measure or estimate, for the
   periods it has figures for.  Every metric member is optional, so an
   object carrying one measured quantity conforms, and a figure may rest
   on estimation for the parts not directly measured if the methodology
   document says what is measured and what is estimated.  An object's
   period and target say what it covers; figures covering part of a
   target or part of a period MUST NOT be presented as though they
   covered the whole.

3.  The Declaration

3.1.  Body

   The body is a single JSON text ([RFC8259], Section 2) whose value is
   either one declaration object or one JSON array of declaration
   objects.  The objects of an array may cover different periods and
   different targets of the same origin: an organization's yearly
   figures beside its months, or an origin beside the services and paths
   it measures separately (Section 5.2).  Figures that differ only in
   their accounting method or functional unit are published as separate
   objects for the same target and period.  A publisher that reports
   both location-based and market-based emissions, as the GHG Protocol's
   dual reporting asks for scope 2 [GHG-SCOPE2], publishes one object
   for each; a publisher with several SCI scores publishes one object
   per functional-unit.  A single object is equivalent to a one-object
   array, and a consumer MUST accept both forms.  Publishers follow
   I-JSON [RFC7493].  A publisher MUST NOT add a top-level member this
   document does not define; other data goes in extensions
   (Section 3.4).  A consumer ignores a top-level member it does not
   recognize and MUST NOT treat its presence as an error ([RFC7493],
   Section 4.2); this document defines no version member, since the
   media type identifies the format.

3.2.  Mandatory Members

   *  *updated* (string): The [RFC3339] date-time at which the object
      was last updated.

   *  *capabilities* (string): "basic" when the server supports no query
      parameter, "extended" when it supports at least one.  The member
      tells a consumer, before it asks, whether a query is worth
      sending; which parameters the server honored is seen in the
      response (Section 2.2).

   *  *provider* (string): Human-readable identification of the
      publisher, such as a name and a role contact address.



Besleaga                  Expires 19 April 2027                 [Page 6]

Internet-Draft     Sustainability-Data Well-Known URI       October 2026


   *  *measurement-method* (string): The method behind the figures.  The
      tokens hardware-metered, hardware-estimated, cloud-billing, and
      third-party-modeled are RECOMMENDED; any other value is a brief
      human-readable description.

   *  *methodology-uri* (string): A URI reference (Section 3.3.1) to a
      document written for people, in any format and language, that
      describes the measurement or estimation method in enough detail to
      interpret the figures.  It says what is measured and what is
      estimated, how figures are allocated to a part of a target, what
      any functional-unit means, which extension names are used, and
      whether any perturbation was applied (Section 6.1).  Nothing a
      consumer does under this document depends on reading it.

   *  *period* (object): The period the object covers, as two members
      start and end, each an [RFC3339] full-date: the period runs from
      the start of the first day to the end of the last, inclusive, and
      end MUST NOT be before start.  Calendar 2025 is {"start":
      "2025-01-01", "end": "2025-12-31"}; a reporting year ending on 31
      March is written as it is.  Whole calendar years and months are
      RECOMMENDED, since they are the periods reports state and the
      periods consumers compare.  Day precision is the finest this
      document offers: reports state their periods as dates, and a day
      is the floor below which figures can be tied to individual
      requests (Section 6.1).

   *  *target* (string): Names what the object is about (Section 1.1).
      It is an opaque protocol element: it MUST NOT be translated or
      transliterated, and it is compared octet-for-octet, except that
      where target-type is origin or the value is otherwise a host name
      the host-name rules of Section 7 apply.  For an organization its
      name is used; for an origin-wide report the origin's host (for
      example "example.com") is RECOMMENDED; other targets are a path
      prefix ("/api/v1"), a service, a tenant, a product, a data source,
      or a device, as target-type can classify.  Figures for a target
      other than the origin are a claim by the origin's publisher about
      that target (Section 5.1).

3.3.  Optional Members

   Numeric members align with the GHG Protocol [GHG-PROTOCOL] and ESRS
   E1 [ESRS-E1]; product-level regimes such as [EU-ESPR] use the same
   quantities.  Unless stated otherwise, a numeric member MUST NOT be
   negative, and a publisher MUST NOT emit a number whose magnitude or
   precision exceeds what IEEE 754 binary64 represents ([RFC7493],
   Section 2.2).

   *  *target-type* (string): Classifies the target as one of
      organization, origin (the publishing origin), path, service,
      product, device, tenant, or data-source.  It does not change the
      syntax or comparison rules of target.

   *  *energy-consumption* (number): Energy consumed by the target
      during the period, in the unit of energy-unit.

   *  *energy-unit* (string): One of Wh, kWh, MWh, GWh; when absent, kWh
      applies.

   *  *carbon-footprint* (number): Gross emissions of the target during
      the period, in the unit of carbon-unit.

   *  *carbon-unit* (string): One of gCO2e, kgCO2e, mtCO2e; when absent,
      gCO2e applies to carbon-footprint and to the scope members.

   *  *carbon-accounting* (string): location-based or market-based
      [GHG-SCOPE2].

   *  *scope-1*, *scope-2*, *scope-3* (number): Direct, purchased-
      energy, and value-chain emissions in the unit of carbon-unit.
      Where they accompany carbon-footprint for the same period they
      SHOULD account for it, and a publisher whose scopes cover only
      part of that figure says so in the methodology document.  These
      MAY be negative where the declared accounting method conveys
      removals or net figures, which the methodology document then
      explains.

   *  *sci-score* (number): Software Carbon Intensity [GSF-SCI], in
      grams of CO2e per functional-unit, which MUST then be present.

   *  *functional-unit* (string): The unit to which sci-score is
      expressed (for example per-request), defined in the methodology
      document.

   *  *carbon-intensity-gCO2e-per-kWh* (number): Weighted carbon
      intensity of the energy consumed.

   *  *estimated-annual-emissions-kgCO2e* (number): Annualized gross
      emissions in kilograms of CO2e regardless of carbon-unit; for a
      period shorter than a year it is an extrapolation described in the
      methodology document.

   *  *renewable-energy* (number): Percentage of energy from renewable
      sources, between 0 and 100 inclusive.

   *  *verifiable-attestation-uri* (string): A URI reference to a
      statement about the published metrics made and cryptographically
      signed by a party other than the publisher; a verifiable
      credential [VC-DATA-MODEL-2] is one such form.  An object carries
      at most one; a target with more than one attestation links an
      index of them from disclosure-uri.

   *  *disclosure-uri* (string): A URI reference to a machine-readable
      index of the target's sustainability disclosures (reports,
      certificates, hosting and energy-source evidence), in any format.

   *  *upstream* (array): The declarations of providers from which this
      object's figures derive (Section 3.5).

   *  *extensions* (object): Members defined outside this document
      (Section 3.4).

   *  *signed* (string): A signature over this object (Section 3.6).

   A declaration object MUST carry at least one numeric metric member or
   at least one of disclosure-uri and verifiable-attestation-uri; a
   metric not reported for the target and period is omitted, and there
   is no in-band "not reported" value.

3.3.1.  URI-Valued Members

   methodology-uri, verifiable-attestation-uri, disclosure-uri, and the
   declaration member of an upstream entry are URI references
   ([RFC3986], Section 4.1), resolved as [RFC3986], Section 5 specifies.
   For a retrieved declaration the base URI is the retrieval URI
   ([RFC3986], Section 5.1.3), so a party that stores, forwards, or
   relays a declaration keeps the URI it retrieved it from.

3.4.  Extensions

   Data that this document does not define is carried in the extensions
   member, an object whose member names are extension names and whose
   values are objects defined by the party that defined the name.  An
   extension name is a URI ([RFC3986], Section 3) under the definer's
   control when the name was minted; a definer without a domain can use
   a UUID URN ([RFC9562]).  A name is an identifier: it is compared as a
   string, written as its definer published it, and never dereferenced.
   A consumer that implements a name's definition processes its value; a
   consumer that does not ignores the value and MUST NOT automatically
   dereference or execute anything within it.  The definer publishes the
   definition wherever it chooses; no registry is defined.  A later
   change of ownership, or the loss, of a domain in a name does not
   change the meaning of a document already published.

3.5.  Upstream Declarations

   A target's figures commonly derive in part from what other providers
   deliver to it: hosting, cloud, content delivery, network transit, or
   electricity.  The upstream member is an array of at least one object,
   each with a declaration member, a URI reference to that provider's
   declaration, and an OPTIONAL role member, a token such as hosting,
   cloud, cdn, network, or electricity.  A provider that reports what it
   delivers to one customer publishes a declaration whose target-type is
   tenant and whose target is an identifier of its choosing, at any URI
   it chooses, for example a per-customer URI it gives that customer;
   its own upstream member, if any, names its sources in turn.  What a
   consumer can conclude from an upstream declaration is described in
   Section 5.5.

3.6.  The signed Member

   The value of signed is a JSON Web Signature in the JWS Compact
   Serialization ([RFC7515], Section 7.1) whose payload is the
   declaration object in which it appears, without the signed member,
   serialized as JSON by the publisher.  In an array each signed object
   carries its own signed member.  The JOSE Header MUST contain alg
   naming an asymmetric digital-signature algorithm; Ed25519 ([RFC9864],
   with the key representation of [RFC8037]) and ES256 ([RFC7518],
   Section 3.4) are RECOMMENDED, and none and MAC algorithms MUST NOT be
   used, since a consumer shares no secret with the publisher.  The
   header MUST also contain cty ([RFC7515], Section 4.1.10) with the
   value sustainability-data+json, which keeps the signature from being
   confused with a JWS produced for another purpose.  The header SHOULD
   carry the verification key as jwk or x5c, so that verification needs
   nothing but the declaration; a publisher that distributes its key out
   of band MAY instead identify it with kid.  A publisher regenerating
   an object regenerates its signature in the same step, so that the
   payload never differs from the object it accompanies.  What a
   verified signature establishes is described in Section 5.4.

3.7.  Formal Definition

   The structure of a declaration is described in CDDL [RFC8610].  Top-
   level members that this document does not define are ignored, as
   Section 3.1 says.

   ; Root: one declaration object, or an array of them
   sustainability-response =
     sustainability-metrics / [* sustainability-metrics]

   sustainability-metrics = {
     ; Mandatory members

   upstream-entry = {

     ? role: tstr,                   ; hosting, cloud, cdn, network, ...
     * tstr => any
   }

   ext-name = tstr                   ; a URI, compared as a string

   The regular expression is an I-Regexp ([RFC9485]), a subset of the
   XSD regular expressions that the .regexp control of [RFC8610],
   Section 3.8.3, uses.

5.  The Nature of the Response

5.1.  Self-Asserted Claims

   Every value in a declaration is a claim of the publisher of the
   origin that served the final response.  Retrieval establishes that
   the origin published these claims and nothing more: a consumer MUST
   NOT treat the presence of a declaration, or of any member in it, as
   verification of a claim, and one that presents, stores, or forwards
   the data MUST NOT represent it as verified.  These are processing
   rules on conforming consumers, not statements about what any party
   may conclude by other means.  The declaration is a discovery
   mechanism: a consumer that needs evidence follows methodology-uri,
   disclosure-uri, verifiable-attestation-uri, and the upstream
   declarations, and checks claims against external sources when it
   matters.








Besleaga                  Expires 19 April 2027                [Page 16]

Internet-Draft     Sustainability-Data Well-Known URI       October 2026


5.2.  Parts of an Origin

   Parts of one origin, such as a service, a path prefix, a device, or a
   product, can account for more or less of what it uses, and a
   publisher may measure or estimate each separately.  Such an object's
   figures are the publisher's allocation of the origin's or the
   organization's resources to that part, by the method the methodology
   document describes.  Parts need not add up to the whole, since
   infrastructure is shared and estimation intervenes, and a consumer
   does not assume that they do; an object for the whole and objects for
   its parts may be present together.

5.3.  Periods and Freshness

   A period is what its two dates say, and no more.  A year and its
   months are two views of the same figures, not additional ones.  A
   consumer that wants a total adds energy-consumption, carbon-
   footprint, and the scope members, after conversion to one unit,
   across objects for one target whose periods do not overlap and that
   declare the same carbon-accounting value or none.  A publisher whose
   accounting day does not start at midnight UTC states its boundary in
   the methodology document; for periods of a month or more the
   difference is immaterial.  A reading is current for the freshness
   lifetime of the response that carried it ([RFC9111], Section 4.2); a
   consumer that keeps it longer revalidates before relying on it, and
   presents the figures as covering their period, not as current.

5.4.  Verifying a Signature

   A consumer that verifies signed MUST reject the member when alg is
   none or a MAC algorithm, when cty is absent or identifies any other
   media type, or when the header carries a crit parameter the consumer
   does not understand.  It determines the acceptable algorithm from the
   key and its own policy, never from alg alone ([RFC8725], Sections 3.1
   and 3.2).  On success it parses the payload as a JSON object and
   reads it as a declaration object; a consumer MUST treat the object as
   unverified when the payload is not one or when the payload's target,
   period.start, or period.end differs from the object's.

   What a verified payload is worth depends on how far the key is
   trusted.  The payload's members take precedence over the members
   around them when the key was obtained out of band, pinned from an
   earlier retrieval, or validated through an x5c chain to an anchor the
   consumer already trusts, with an end-entity certificate that
   identifies the publisher ([RFC9110], Section 4.3.4).  "Out of band"
   means from a source the consumer chose independently of the
   declaration, never from a URI the declaration or its JOSE Header
   names.  Any other key is trusted no further than the declaration



Besleaga                  Expires 19 April 2027                [Page 17]

Internet-Draft     Sustainability-Data Well-Known URI       October 2026


   carrying it, and the members served by the origin remain the ones the
   consumer uses.  A key that arrives in its own header is as self-
   asserted as the metrics: whoever can publish the declaration can
   publish a key.  A verified signature establishes integrity and, with
   pinning, continuity of authorship; it establishes nothing about
   accuracy (Section 5.1).  An absent signed member means only that the
   publisher did not sign; a member that fails to verify leaves the
   object unverified, never false.

5.5.  Evidence and Upstream Consistency

   The methodology document explains the figures.  An attestation at
   verifiable-attestation-uri speaks to their authenticity only once the
   consumer has retrieved it and validated it against an issuer it
   trusts. disclosure-uri leads to the reports and certificates behind
   them.

   Where an upstream publishes a tenant declaration about what it
   delivers to this target, a consumer MAY compare the two for the same
   period after conversion to one unit.  A target whose declared scope
   covers what the upstream delivers cannot have consumed less energy,
   or caused fewer emissions, than the upstream states it delivered, a
   shortfall within rounding aside.  A smaller figure is an
   inconsistency between two claims, something to investigate and not a
   conformance failure.  The comparison is limited: the format does not
   say whether a target's scope covers a given upstream, it carries no
   per-upstream share, and carbon-footprint is comparable only where
   both objects declare the same carbon-accounting value or neither
   does.  A consumer that follows upstream declarations applies the
   bounds of Section 6.

6.  Security Considerations

   A declaration is meant for automated ingestion from an origin the
   consumer does not control.  The threats, and what answers each:

   *  spoofing: mandatory HTTPS, taking a declaration as a claim of the
      publisher of the origin that served the final response, and the
      signed member;

   *  tampering: HTTPS, the registered media type, and the signature;

   *  false or selective figures: the methodology link, the attestation
      channel, and the rule that a consumer never labels a claim as
      verified (Section 5.1);

   *  disclosure through the figures: Section 6.1.




Besleaga                  Expires 19 April 2027                [Page 18]

Internet-Draft     Sustainability-Data Well-Known URI       October 2026


   Nothing here makes a published figure true: an attacker who controls
   DNS, the certificate, or the origin can publish false data, and key
   pinning is the only defense against such an attacker removing
   signatures.  A publisher behind a content delivery network or reverse
   proxy serves the bytes it produced unchanged, content codings aside,
   since an intermediary that rewrites the data invalidates any signed
   member.

   A consumer:

   *  SHOULD bound the time, size, and redirects of every fetch,
      dereference only "https" references, and refuse URIs that resolve
      to private or link-local addresses;

   *  MUST limit the bytes and objects it accepts and treat an excess as
      an error;

   *  SHOULD parse with a JSON parser hardened against untrusted input
      ([RFC8259], Section 12) and treat every value as data; one whose
      parser exposes duplicate member names SHOULD reject an object
      containing them;

   *  that follows upstream declarations MUST NOT go deeper than three
      declarations below the one it started from, MUST refuse any URI it
      has already retrieved during the walk, and MUST bound the total
      number of retrievals in one walk.

   A server that computes responses to query parameters on demand SHOULD
   rate-limit requests to the well-known URI and SHOULD cache what it
   computes.

6.1.  Privacy Considerations

   A declaration is readable by whoever the publisher lets retrieve it.
   Energy and utilization figures can reveal capacity and load patterns,
   precise metrics can reveal hardware, per-part objects reveal which
   services and paths exist, and contact strings can carry personal
   data.  The publisher decides what to publish and at what aggregation.
   A period is a day or longer (Section 3.2), and real-time telemetry is
   NOT RECOMMENDED.  A publisher MAY perturb the published values by
   multiplicative noise within 1% of the true values to blunt hardware
   fingerprinting.  Noise is applied once, at generation time,
   deterministically per period, and consistently across arithmetically
   related members, including any annualized or derived member, so that
   ratios are preserved and no unperturbed member discloses a perturbed
   one.  The methodology document states that noise is applied and
   bounds its magnitude.  A publisher SHOULD aggregate or omit any
   metric that could be linked to individual users or small groups, and



Besleaga                  Expires 19 April 2027                [Page 19]

Internet-Draft     Sustainability-Data Well-Known URI       October 2026


   SHOULD use a role rather than a personal contact address in provider.

7.  Internationalization Considerations

   A declaration is JSON and therefore UTF-8 ([RFC8259], Section 8.1).
   The following are protocol elements: member names, the values of the
   enumerated members, the RECOMMENDED measurement-method tokens, the
   role tokens, extension names (ASCII URIs, never IRIs), functional-
   unit, the date members, the URI-valued members, and signed.  They are
   compared octet-for-octet where this document compares them, and never
   case-folded, normalized, translated, or localized.  Where target is a
   host name it is compared case-insensitively ([RFC3986],
   Section 3.2.2), and an internationalized host is given in A-label
   form ([RFC5890], Section 2.3.2.1).  The value of provider, a
   measurement-method value outside the RECOMMENDED set, and human-
   readable values within extensions are text.  Their language is
   conveyed at the HTTP layer by Content-Language ([RFC9110],
   Section 8.5).  A consumer that displays such text SHOULD render it
   under the Unicode Bidirectional Algorithm [UAX9] and isolate it from
   surrounding text.  No in-document language-tagging mechanism is
   defined.

Appendix A.  Worked Example: A Live Deployment

   This appendix walks through one deployment of this specification,
   from figures to verified retrieval.

   1.  *Figures.* A small hosted service has no metering.  It multiplies
       an average draw for its container (an assumed 3 W, or the
       platform's reported average where available) by the hours in the
       completed month and converts with a published national grid
       intensity (245 gCO2e/kWh).  The draw is assumed or estimated and
       the conversion is a model, so measurement-method is third-party-
       modeled; the methodology document states the formula, the basis
       of each month's draw, the intensity source, and what is not
       covered.



Besleaga                  Expires 19 April 2027                [Page 26]

Internet-Draft     Sustainability-Data Well-Known URI       October 2026


   2.  *Declaration.* The object for the last completed month carries
       target (an identifier of the service), target-type service,
       capabilities extended (it also answers ?start= and ?end= with its
       months), a disclosure-uri and a verifiable-attestation-uri.  The
       platform publishes no declaration, so there is no upstream member
       and the methodology document says so.

   3.  *Signing.* The publisher signs the serialized object with an
       Ed25519 key (alg Ed25519, cty sustainability-data+json, the
       public key as jwk) and inserts the result as signed; each object
       of the monthly array likewise.

   4.  *Serving.* /.well-known/sustainability-data over HTTPS, with
       Content-Type: application/sustainability-data+json, Cache-
       Control: max-age=3600, and an ETag.

   5.  *Attestation.* An issuer that has reviewed the methodology and
       the figures issues a verifiable credential [VC-DATA-MODEL-2],
       signed with a key it publishes and served at the verifiable-
       attestation-uri.  Its credentialSubject carries the derivation
       model, its constants and formulas, and the entered months; it is
       re-issued when any of them changes.  Here the issuer is not
       independent of the publisher; the credential says so, and a
       consumer records the attestation as no stronger than that
       relationship allows.

   6.  *Retrieval.* A consumer fetches the declaration, verifies signed
       with the pinned key, fetches and verifies the credential, and
       recomputes the figures from its model.  It records: a claim of
       the origin; integrity verified; attested by that issuer; accuracy
       unknown.

   7.  *Static variant.* An organization with a yearly report writes the
       object by hand, or produces it with an offline tool that signs
       and writes one file, and uploads it.

C.1.  Since -08

   This revision changes the wire format and restructures the document,
   in answer to the Independent Submissions Editor's comments on -08 and
   the ART-area early review of -07.  A -08 document is not a valid -09
   document: the reporting-period member is replaced by period.

   Wire format:

   *  reporting-period (a calendar string YYYY, YYYY-MM, or YYYY-MM-DD)
      is replaced by period, an object with start and end, each an RFC
      3339 full-date, inclusive, so that any reporting year can be
      written and every date in the document is an RFC 3339 production.
      Whole calendar years and months remain RECOMMENDED.  The UTC rule
      and the rule to publish a non-calendar year as its months are
      gone.

      granularity remains, as a filter on whole calendar years, months,

      the same period they SHOULD account for it; and pinning a key
      establishes continuity of authorship, not identity, which is what
      the precedence rule rests on.
